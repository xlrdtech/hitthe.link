PRD — Native Voice Mode targeting a Remote Control session

Verdict this PRD answers to: B — requires a first-party change. Everything in Part 1 is buildable by qi today. Part 2 is the ask for Anthropic. They are kept apart deliberately so a B never gets shipped disguised as an A.

PART 1 — WHAT QI CAN BUILD NOW (path A)

Ordered by value-per-hour. Each is independently shippable; none touches the canonical route.

A1. Fix the ASCII destroyer (≈30 min, highest value/effort on the board)

Defect, measured: tui-inject.js sanitize() runs s.replace(/[^\x20-\x7E]/g, ' '). Every accent, em-dash, curly quote and emoji in an injected turn is silently replaced with a space. Every inbound rail — SMS, Beeper, voice, mail — funnels through it. Why it matters beyond aesthetics: qi's client threads contain names with accents. A message relayed about "José" arrives as "Jos ". That is a correctness bug in the comms rail, not a cosmetic one. Fix: keep the control-character strip, drop the non-ASCII strip. tmux send-keys -l is UTF-8 safe; the mangling is self-inflicted. Preserve the existing chunking. Acceptance: inject José — 🎭 "curly" and assert the transcript line matches byte-for-byte.

A2. Prove Channels × Remote Control compose (≈1 h, unblocks everything else)

Both docs are silent on the combination; ~/.claude/remote-settings.json already says {"channelsEnabled": true}, so nothing needs enabling. Experiment: start a session with --channels plugin:telegram@claude-plugins-official --remote-control; send a Telegram message; then check (a) does it land as a turn, (b) does it appear in the claude.ai/code mirror, (c) does Claude's reply reach Telegram, (d) does a permission prompt relay to the phone. Why it is the linchpin: if channel-injected turns DO appear in the /rc mirror, then a custom voice channel becomes an A-path that inherits /rc's fidelity — no ASCII mangling, no Escape truncation, structured turns, and remote-answerable permission prompts. Record the answer either way — it is currently undocumented by Anthropic, so this is new information regardless of outcome.

A3. Build a voice channel (the real prize, gated on A2)

A channel is just an MCP server declaring capabilities.experimental['claude/channel'], emitting notifications/claude/channel {content, meta} and registering a reply tool. qi already owns every other piece: STT, TTS, VVS, barge-in, the 4461 relay. This is NOT native Voice Mode and this document will not call it that. It is a first-party supported injection path carrying voice, which is strictly better than tmux keystrokes and strictly worse than native Voice Mode. State it that way to qi every time. Also declare capabilities.experimental['claude/channel/permission'] — permission prompts then relay to his phone and are answerable remotely, with local terminal and remote both live and first-answer-wins. That directly serves the no-human-at-the-desk requirement.

A3b. ⚠️ DUAL-INGRESS COLLISION — the trap that fires the day RC + voice are both on

Measured: /rc reaches the Claude Code session (keyed by machineID + claude.ai OAuth, addressed by session id 5922006e-…). Every Xen rail reaches the pane (%0 via tmux send-keys). They land in the same transcript today only because pid 82902 happens to occupy pane %0 — that is a coincidence of placement, not a shared address.

Two concrete failures follow, and neither is theoretical:

  1. Double-delivery. omnimind's 5-second md5 dedup lives in /tmp/xen-tui-dedup/ and is

invisible to the bridge. The same utterance arriving via claude.ai Voice Mode and the VVSVEI rail lands twice, as two user turns.

  1. Barge-in truncates the remote turn. voiceTrigger:true fires Escape into pane %0 before

typing. If an RC turn is in flight, that Escape kills it mid-execution — from claude.ai it looks like the session randomly aborted.

Design rule: PICK ONE INGRESS PER UTTERANCE. Do not merge them. Either the bridge owns the turn (and the tmux rail must suppress, including its Escape), or the pane owns it (and RC is detached). A shared dedup key across both planes is the minimum if both must stay armed. Fidelity note: choosing the RC ingress removes the sanitizer loss entirely — no ASCII stripping, no newline flattening, no label prefix — at the cost of the barge-in escalator that canon 10 requires. That trade is qi's to make, and it is a real trade, not a free upgrade.

A3c. There IS a protocol-level path already in the binary — currently unused

Bundle strings show peer messaging by uds:<socket> / bridge:<session id> with [uds-messaging] Routed user message to queue (priority=…) and sendToUdsSocket, tied to RC via isUdsEnableRemoteControlEnabled. Measured: zero references to uds: or sendToUdsSocket anywhere in the Xen tree. This is a documented-in-binary, structured, non-TTY way to deliver a user turn — i.e. exactly the "protocol-level, not keystroke-level" rail every Xen injector currently lacks. Worth a spike before building anything new on send-keys.

A4. Guard the auth-mode conflict (≈15 min, prevents a silent outage)

Measured: RC refuses to run when an API key is present in the environment — "Remote Control is only available when using Claude via api.anthropic.com… unset it (or run in a shell without it)". If ANTHROPIC_API_KEY ever enters pane %0's shell, RC silently dies while the tmux rails keep working — it will present as "voice is broken" and waste hours. Build: extend the existing health sweep to assert ANTHROPIC_API_KEY is unset in the seat's env AND remoteControlAtStartup is still true; alarm loudly if either flips.

A5. Instrument what RC actually does (≈1 h)

DNS cannot separate the bridge from the API — 160.79.104.10 serves api.anthropic.com, claude.ai and bridge.claudeusercontent.com alike, so none of the seat's 11 sockets can be identified by IP. Use the mitmproxy already installed, or TLS SNI capture, to confirm the live wss://bridge.claudeusercontent.com socket and observe the turn envelope. Converts the biggest INFERRED claim in the architecture doc into a MEASURED one.

PART 2 — THE FIRST-PARTY ASK (path B)

For the Claude web + Remote Control teams. One sentence: let the voice controller attach to a target that is not a hosted chat conversation.

B1. UI

claude.ai/code: expose the Voice Mode entry point when an /rc session is attached. Today the control is absent on this surface by product decision, not by capability.

B2. Voice controller target-adapter interface

Replace the implicit VoiceModeController → HostedChatConversation coupling with VoiceModeController → VoiceTarget, implemented by both HostedChatConversation and RemoteControlSession. Required surface (full rationale in the architecture doc): attach/detach (detach must NOT end the session — an /rc session outlives the voice attachment), submit_user_turn, stream_assistant_text with a speakable flag, signal_turn_boundary, cancel(reason) safe mid-tool-execution, subscribe_events, get_transcript.

B2b. ⭐ THE MEDIA PLANE IS NOT THE CONTROL PLANE (qi, 2026-08-09)

qi: "socket is less usable for the voice than webrtc sfu according to perplexity." Correct, and it reframes the ask. The RC bridge is wss://bridge.claudeusercontent.com — a WebSocket. A WS carries text turns perfectly well, but native Voice Mode needs low-latency bidirectional audio: jitter buffering, echo cancellation, packet-loss concealment, and sub-100 ms barge-in. That is WebRTC/SFU territory, not WS-over-TCP. Head-of-line blocking alone makes TCP a poor audio carrier. ⇒ The design is two planes, not one:

  • Control plane — the existing WS bridge, keyed by session id. Carries turns, tool events,

permission prompts, transcript sync. Already exists.

  • Media plane — a WebRTC path (SFU or direct peer) carrying mic → STT and TTS → speaker,

joined to the same session id. Does not exist for /rc. The adapter in B2 therefore binds a session identity shared across both planes; it does not tunnel audio through the control socket. Any proposal that streams voice over the WS bridge should be rejected on latency grounds before it is built.

B3. The speakable classifier — the piece that does not exist anywhere

An /rc stream carries diffs, file paths, command output and tool JSON. TTS must never read a unified diff aloud. Nothing in the current stack marks which deltas are speech-bearing. This is net-new work and it is the technical heart of the ask.

B4. Silence contract for long tool calls

Chat voice assumes sub-second turns. An /rc turn can run five minutes silent. Needed: progress narration or earcons, a defined timeout, and barge-in during execution (not just during speech). Anthropic already ships a "Still working" nudge for exactly this — it just has no audio form.

B5. Spoken permission prompts

The object model already exists (Channels relays permission_request with request_id, tool_name, input_preview, and a 5-minute dialogExpiry). What is missing is rendering it as speech and accepting a spoken answer. Safety flag: "Claude wants to run rm -rf build/, approve?" spoken aloud is a materially different risk surface from a tappable button — destructive-command confirmation by voice needs its own design, not a naive read-aloud.

B6. Privacy boundary to state explicitly

While /rc is connected, the transcript including tool activity is stored on Anthropic servers (30-day default; ZDR enterprise-only). Adding a voice channel adds audio. Session 0 handles real client data — this must be surfaced to the user, not buried.

ACCEPTANCE TESTS

  1. A1: inject José — 🎭 "curly"; transcript matches byte-for-byte. (fails today)
  2. A2: channel turn appears in the claude.ai/code mirror. (unknown today — this is the test)
  3. A2b: permission prompt raised locally is answerable from the phone; first answer wins.
  4. A4: with ANTHROPIC_API_KEY set in a scratch shell, the guard alarms before RC dies.
  5. A5: a live wss://bridge.claudeusercontent.com socket is captured and its turn envelope

recorded.

  1. B (end-state): speaking on claude.ai/code with an /rc session attached causes pid 82902 in

pane %0 to execute the turn, and the spoken reply returns — with the transcript identical to a typed turn.

  1. Regression, non-negotiable: after every change above, VVS → tmux 0 → Xen → Claude Code

still works unchanged. The canonical route is never replaced, only added to.

EXPLICIT NON-CLAIMS

Dictation is not Voice Mode. A text channel is not Voice Mode. A custom voice channel is not Voice Mode. Only B1–B5 delivers what qi actually asked for; everything in Part 1 is scaffolding that makes the eventual binding better and the current rail less lossy.
