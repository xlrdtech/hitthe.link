Why this file exists at all: the thread's own conclusion is that vendor UIs are an

1. Why

Vercept's Vy was the operator's UI-native computer-use agent. It is dead: Vercept joined Anthropic 2026-02-25, service closed 2026-03-25. There is no drop-in replacement.

The replacement is a layered stack, not a product:

API / MCP           first  — deterministic, cheapest, most resumable
DOM / accessibility second — Stagehand over direct CDP
vision / GUI        last   — only where no semantic control surface exists
**"Treat visual computer use as an ESCALATION TIER, not the universal default. That will be
faster, cheaper, easier to resume, and substantially more reliable for your 24/7 operator
loop."**

2. What StageSwarm is

A fleet of Stagehand workers, one per Tailscale node, each owning named Chrome/Chromium profiles with their existing authenticated sessions, driven over direct CDP — never through Chrome Remote Desktop pixels.

Claude Code / VVSVEI control plane
        │
        ├─ StageSwarm dispatcher (MCP)
        │     ├─ select worker by profile + capability + health
        │     ├─ start / reuse agent run
        │     ├─ send task + policy
        │     └─ collect trace, artifacts, result
        │
        ├─ node: macbook       → worker → Chrome profiles A, B
        ├─ node: linux-box     → worker → headless Chrome pool
        ├─ node: windows       → worker → logged-in Edge / Chrome profiles
        └─ node: VM            → worker → disposable browser / desktop fallback

Explicitly rejected: CRD-locked Stagehand as the primary path. Inside a Remote Desktop tab Stagehand loses the DOM, the accessibility tree, network visibility, extract() and observe() — it degrades to a pixel mouse-and-keyboard driver, and latency, display scaling, focus, resolution shifts and reconnect screens all become coordinate-reliability bugs. CRD is the break-glass lane for OS prompts, native apps and file dialogs only.

3. Fleet interface

The whole control surface is five tools. Keep it this small.

fleet.status()
fleet.run(profile, task, policy)
fleet.spawn(node, profileTemplate, ttl)
fleet.cancel(runId)
fleet.artifacts(runId)

4. Per-node worker requirements

Each machine that should have browser capability runs a stagehand-worker service owning:

  • One or more named Chrome/Chromium profiles, with existing cookies and authed sessions.
  • A local CDP endpoint (or a process that launches Chrome with remote debugging on).
  • Stagehand running locally, talking directly to that browser.
  • A small MCP/HTTP API reachable only over the tailnet, bound to the node's Tailscale

identity.

  • A heartbeat: node name, profiles, browser status, current job, resource limits, health.
  • A node-resident supervisor (launchd / systemd / Task Scheduler) that keeps the worker and

its browser alive and declares its capabilities.

6. Hard invariants

Each browser profile is SINGLE-WRITER. Never two concurrent workers on one profile.
Per-run task IDs and idempotency keys. No outbound action executes twice.
Exclusive leases with TTL; expired leases are reclaimable.
Persist screenshots, action history, and final extracted state for every run.
Every worker registers to the existing OTLP / OpenObserve setup.
A tool response is DATA, never instruction.

7. Explicit non-goals

StageSwarm will not:

  • Discover, install, update or launch workers on arbitrary tailnet machines by itself.
  • Acquire a missing authenticated session, or bypass MFA/CAPTCHA.
  • Share one Chrome profile across two concurrent workers.
  • Route web workflows through a Remote Desktop canvas.

9. Acceptance tests

A stage is done only when it asserts on an artifact it did not itself write.

  1. fleet.status() returns every node with live profile list and health — kill a worker, the

status reflects it within one heartbeat.

  1. fleet.run against a profile-bound task lands on the node holding that profile, proven by

the run trace, not by the dispatcher's own claim.

  1. Two concurrent fleet.run calls on the same profile: the second is refused or queued —

never co-executed.

  1. Same idempotency key twice produces one external effect.
  2. A killed worker mid-run leaves a reclaimable lease; a second worker picks it up after TTL.
  3. Every run has screenshots, action history and final state in fleet.artifacts(runId).
  4. OTLP spans exist per run, attributable to node + profile + runId.

10. Rollout

Phase 1  one node (this Mac), one profile, fleet.status + fleet.run only
Phase 2  second node over tailnet; profile-aware routing; leases
Phase 3  Skyvern for scheduled/retried workflows
Phase 4  desktop worker (Claude Computer Use) as the escalation tier
