REVIEW — Claude Web Voice Mode Unified with Canonical tmux Harness

Reviewed 2026-07-31 by Xen. Source: inbox_/claude-web-voice-tmux-prd.pdf, 7 pages.

Verdict

The PRD is sound in structure and wrong in one load-bearing assumption. Layering, scope boundaries, phase ordering and deferrals are all argued rather than assumed — the decision to hold OmniRoute until the browser loop is stable is correct, and rejecting APK modification is correct.

One assumption decides whether any of it functions, and the PRD files it under Open Questions rather than Constraints.

THE BLOCKER

Open question, as written: *"Does the exact Claude web Voice Mode control surface remain fully
usable in the persistent browser session path being targeted?"*

Browserbase is a cloud browser. Cloud browsers have no microphone and no speaker.

Voice Mode requires live microphone capture and audio playback. A headless Chrome running in a datacenter container has neither device. The audio hardware is in qi's room; the browser is in Browserbase's.

Consequence: Phase 1 (persistent context) and Phase 2 (Stagehand control) can both pass every stated success criterion — session survives restarts, UI recovers after DOM shifts, reconnect works from multiple devices — and the product still cannot hear him. The failure is invisible to the phase gates as written, because none of them test audio.

This is not a risk with a mitigation. It is an architectural incompatibility between two requirements the PRD holds simultaneously.

THE FORK

"anywhere access through reconnectable sessions" requires the browser in the cloud "Claude web Voice Mode as the only voice surface" requires a microphone in the room

These cannot both hold. The only bridge between them is piping local audio into the remote session over WebRTC, which:

  • adds a network hop to a real-time loop, where latency is the product;
  • introduces a second failure domain (media transport) on top of the two the PRD already

worries about (session expiry, UI shift);

  • and reintroduces exactly the brittleness the move to persistent cloud sessions was meant to

eliminate.

The PRD's own non-functional requirement — "Fast actionability" — argues against it.

THE VERSION THAT SURVIVES

Keep the frontend requirement. Move the runtime.

Voice/UI surface Claude web chat Voice Mode UNCHANGED Browser runtime LOCAL Chrome, durable profile was: Browserbase cloud Session persistence local profile dir + supervised relaunch AI browser operator Stagehand, pointed at local CDP UNCHANGED in role Canonical brain existing tmux harness UNCHANGED Model routing OmniRoute, still deferred UNCHANGED

What is preserved: the exact maintained frontend, AI-assisted recovery from unmapped UI, tmux as source of truth, restart-safe supervision, and every functional requirement except one.

What is lost: FR2's "reconnect from anywhere" becomes "reconnect to the machine with the microphone." That is the whole cost.

Which means the constraint to re-open is in Out of Scope, not In Scope. Local paths were ruled out, and local is where the microphone is.

Secondary findings

1. "No verified documented official bridge" — correct, and it stays that way. Voice Mode is a first-party UI feature with no public API. Any bridge is browser-level by necessity, which makes Stagehand's observe() / act() / extract() the right primitive choice — that part of the tooling decision holds regardless of where the browser runs.

2. FR6's recovery order is well specified — reconnect session, re-observe UI, reacquire targets, resume bridge. Add one step at the front: verify audio devices are present and bound. Under the local architecture that is the failure that will actually happen (device stolen by another app, default output drifted), and it is the one recovery step the current order cannot detect.

3. Transcript granularity — the open question worth answering first. Raw utterances, summarized checkpoints, or both determines the tmux bridge's shape. Recommend both, with raw as the durable artifact and summaries as derived, because a summary that turns out wrong cannot be un-summarized. There is precedent from today: verbatim capture with corrections left visible beat every attempt to store the cleaned version.

4. Phase gates need an audio criterion. As written, no phase tests whether a human's voice reached the model and a reply reached their ears. Add it to Phase 1 — before any Stagehand work — so the blocker surfaces on day one rather than after two phases of green.

One-line summary

The frontend choice is right, the brain choice is right, the operator choice is right, and the runtime location is wrong — because the microphone does not live in the cloud.
