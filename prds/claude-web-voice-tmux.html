Claude Web Voice + tmux — Post-Swarm Decision Document

Inputs: PRD (claude-web-voice-tmux-prd.pdf), review (claude-web-voice-tmux-prd-REVIEW.md), 6 investigator scopes, 3 adversarial lenses. Date: 2026-07-31. Every claim below is tagged [VERIFIED — url], [VERIFIED — local] (run on this M4), or [INFERRED].

1. THE VERDICT ON THE BLOCKER

The review's blocker was: "Cloud browsers have no microphone and no speaker. Claude web Voice Mode cannot function inside a Browserbase session. This is not a risk with a mitigation — it is an architectural incompatibility. 'Anywhere access' and 'a local microphone' cannot both hold."

Split verdict. The recommendation survives. The reasoning is refuted. The word "impossible" was never earned.

Where the review was right, and stronger than it knew. Browserbase's create-session API has no audio parameter, no media-permissions parameter, and no args/launch-flags field at all — the full parameter set is projectId, extensionId, timeout, keepAlive, region, userMetadata, proxies, proxySettings, browserSettings{context, viewport, blockAds, solveCaptchas, recordSession, logSession, advancedStealth, verified, captcha*, os, allowedDomains, ignoreCertificateErrors} [VERIFIED — https://docs.browserbase.com/reference/api/create-a-session]. Session Live View documents watch/click/type/scroll/file-upload/clipboard and never mentions audio in either direction [VERIFIED — https://docs.browserbase.com/features/session-live-view]. docs.browserbase.com/llms.txt contains zero pages mentioning audio, microphone, media devices, or WebRTC [VERIFIED — https://docs.browserbase.com/llms.txt]. So the standard Chrome fake-audio workaround is not merely inadequate — it is unreachable by construction. Browserless hosted publishes an 11-flag allowlist that excludes every fake-media flag [VERIFIED — https://docs.browserless.io/baas/chrome-flags], with a user reporting NotFoundError: Requested device not found after passing them anyway [VERIFIED — https://github.com/browserless/browserless/issues/1764]. Steel's own CDP service runs --headless=new and explicitly disables AudioServiceOutOfProcess [VERIFIED — https://github.com/steel-dev/steel-browser/blob/main/api/src/services/cdp/cdp.service.ts]. The three named agent-cloud-browser vendors are dead for live voice.

Where the review was wrong, and all three lenses caught it independently. Remote browsers with a working local microphone are a shipping, documented, commodity product — just not in the agent-automation category:

  • Kasm Workspaces: "The local microphone can be used within the Kasm session by enabling this option" and "Audio produced within the session can be toggled on and off via the Sound item" [VERIFIED — https://kasm.com/docs/latest/user_guide/control_panel.html]; mechanism documented on the sibling webcam page as browser Media Capture → virtual device mapped into the container [VERIFIED — https://kasm.com/docs/latest/guide/webcam_passthrough.html].
  • neko: "Neko allows you to capture the microphone on the client machine and send it to the server using WebRTC", config capture.microphone.enabled + capture.microphone.device (a PulseAudio virtual mic) [VERIFIED — https://github.com/m1k1o/neko/blob/master/webpage/docs/configuration/capture.md].
  • AWS AppStream 2.0 RTAV redirects local webcam + microphone into a cloud streaming session from a Chromium client [VERIFIED — https://docs.aws.amazon.com/appstream2/latest/developerguide/web-browser-video-audio.html].

The review reasoned from hardware to capability and skipped the virtualization layer the entire remote-desktop industry runs on. getUserMedia is an API boundary, not a hardware fact. And the impossibility claim itself was never tested — no one in this swarm (or in the review) ran enumerateDevices() inside a Browserbase session. The honest status is undocumented and unsupported, not proven impossible. That distinction matters because the review criticized the PRD for exactly this move — promoting an untested inference to a Constraint — and then made it.

Credit where due: the three adversarial lenses were right and the review's headline finding was overstated. Being wrong out loud is the point of running the swarm.

And the swarm found two blockers that neither the PRD nor the review names, both of which outrank the microphone.

NEW BLOCKER A — the Terms of Service (this is the real one)

Consumer Terms §3, "Use of our Services," item 7, verbatim: "Except when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it, to access the Services through automated or non-human means, whether through a bot, script, or otherwise." [VERIFIED — https://www.anthropic.com/legal/consumer-terms — independently re-fetched 2026-07-31]. Item 4 additionally prohibits scraping data from the Services.

Reinforcing: "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications" and "Anthropic reserves the right to take measures to enforce these restrictions and may do so without prior notice" [VERIFIED — https://code.claude.com/docs/en/legal-and-compliance]. Enforcement is not theoretical: consumer OAuth tokens were blocked for third-party harnesses (OpenClaw, OpenCode, Roo Code, Goose) across Feb–Apr 2026 [VERIFIED — https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/].

There is no audio, speech, voice, TTS, STT, or realtime endpoint anywhere in the Claude API — the complete surface is Messages, Message Batches, Token Counting, Models, and beta Files/Skills/Agents/Sessions/Environments [VERIFIED — https://platform.claude.com/docs/en/api/overview]. So the API-Key exception in §3(7) is structurally unavailable for Voice Mode. There is no compliant automated path to this feature, now or on any announced roadmap.

The PRD's Risks table lists UI drift and session expiry. It does not list "the Max account is terminated and the whole system dies." That belongs in the table, and the review missed it too.

NEW BLOCKER B — Cloudflare bot management, reproduced on this machine

https://claude.ai/new loaded in a CDP-attached Chrome on this M4 returned a Cloudflare interstitial ("Performing security verification", Ray ID a23f72d08fc2b8d8) and never rendered app DOM — document.querySelectorAll('[data-testid]').length === 0 across repeated checks. Other tabs in the same browser (perplexity.ai) were also challenged, so this is bot-management against the automation-flagged browser instance generally [VERIFIED — local]. This bites the local architecture identically to the cloud one, and it is the nearest wall in wall-clock terms.

NEW BLOCKER C — there is no working microphone on this Mac

Live re-check, 2026-07-31: the only enumerated audio inputs are BlackHole 2ch, Phound Audio Device, Jump Desktop Microphone, Jump Desktop Audio, xen, qi, in, out, ZoomAudioDevice — every one virtual, no physical mic present — and the current default input is in, a Loopback device [VERIFIED — local]. Earlier in the swarm, a 1.2s capture from the default input measured RMS 0.000e+0 / peak 0.000e+0 / peakHz 0: dead silence [VERIFIED — local]. Voice Mode would open, connect, and hear nothing. Also: the currently-running Chrome executes from /Volumes/X31/Applications/Google Chrome.app [VERIFIED — local], a volume canon documents as physically flapping — a "durable local profile" anchored there is not durable.

Net: the microphone blocker is not the reason to abandon the cloud. Browserbase's missing audio API is. And the ToS is the reason to think hard about the whole PRD.

2. THE ARCHITECTURE DECISION

LOCAL. Real Chrome on M4, dedicated user-data-dir, launched and supervised by tmux, driven by Stagehand over CDP. Not cloud. Not neko/Kasm. Remote reach is decomposed into three channels with three different owners.

This is picked, not hedged. What it costs is named below.

What LOCAL costs, stated plainly: FR2's "reconnect from anywhere" no longer means "voice from any device anywhere." It splits into three channels with wildly different fragility, and only two of them work today.

  • Brain — tmux over mosh + Tailscale. Already live: m4 100.97.145.50, 16pro 100.77.15.88, exedus-1 100.120.189.18, Remote Login on, tmux sessions xen/xen2/claude_m4 persisting for days [VERIFIED — local]. Near-zero risk. Carries zero audio.
  • Eyes/hands — Screen Sharing (com.apple.screensharing => enabled [VERIFIED — local]) or CDP over an SSH tunnel through Tailscale. Solid. Needs no audio. Note: every VNC-family option has no audio channel in the protocol at all [VERIFIED — https://en.wikipedia.org/wiki/VNC] — label them so nobody spends a phase discovering it. Parsec is struck outright: mic passthrough is Windows-host-only [VERIFIED — https://support.parsec.app/hc/en-us/articles/32380350695956 — via search extraction; the page 403s to direct fetch].
  • Mouth/ears — the only hard channel, and it is its own ranked decision, not a property of the session layer. Primary: Jump Desktop Fluid Mac→Mac mic redirection, already provisioned and running on this box (/Library/Audio/Plug-Ins/HAL/JumpAudioMic.driver loaded, Jump Desktop Connect.app PIDs 284/422, "Jump Desktop Microphone" selectable as input, TCC grants com.google.Chrome|2 and com.p5sys.jump.connect|2 already present) [VERIFIED — local] — but vendor-documented as Mac-client-to-Mac-host only, with iPad/iOS explicitly not supported as of the changelog [VERIFIED — https://changelog.jumpdesktop.com/microphone-forwarding-for-fluid-4CTeHS]. qi's only currently-online remote device is an iPhone. That is the cost: remote voice works from a Mac, and is unverified from the phone. Fallback: SIP/PSTN audio into an existing virtual input (freeswitch/ tree, ~/bin/xen-call, voice-duplex.py, BlackHole + four Loopback devices all present [VERIFIED — local]) — carrier-grade real-time, at the cost of 8 kHz narrowband into a VAD tuned for wideband [INFERRED].

Why not neko/Kasm despite refuting the fork. The mechanism is real and documented. But it inserts a WebRTC hop and a second getUserMedia into a real-time barge-in loop with zero published latency numbers and no published report of anyone running Claude Voice Mode through it [unknown]; and Kasm's own docs note users may need to click inside the session before audio starts, while both options require qi's local browser to grant mic and stay connected — a tap and a presence dependency, colliding with C4 and C21 [VERIFIED — https://kasm.com/docs/latest/user_guide/control_panel.html]. It stays on the bench as the Plan B if remote-mic quality from the phone proves unacceptable. It is not the day-one architecture.

Why not the plane-split despite it being the cleanest answer. It is genuinely elegant: Voice Mode runs first-party on whatever device qi holds, the conversation is the bus (transcripts persist to chat history, and "you can switch between text and voice within the same conversation — your previous context carries over" [VERIFIED — https://support.claude.com/en/articles/11101966-use-voice-mode]), and the orchestration browser attaches to the same conversation server-side. It also has the lowest ToS exposure, because a human is genuinely using the app. Two reasons it is not the decision: it rewords FR3 from "web Voice Mode" to "first-party Voice Mode," which is qi's call not mine; and its write direction — tmux-injected text picked up mid-live-voice-turn — is untested, with adjacent evidence against it (MCP connectors reported non-functional in voice chat, anthropics/claude-ai-mcp#146, closed as not planned) [INFERRED from that issue's existence; I did not verify the issue text directly]. Recommendation: adopt LOCAL now, and run the plane-split as a 20-minute parallel probe, because if the write direction works it is strictly better.

3. CONCRETE NEXT STEPS

T0 — five minutes, and nothing else matters until it passes

Route a physical microphone with signal into macOS and make it the default input. Right now there are nine inputs and all nine are virtual [VERIFIED — local]. Assert non-zero: capture 1s from the default input and require RMS > 1e-4. If this fails, every other step is theater.

Second five-minute item: move Chrome off /Volumes/X31 [VERIFIED — local] and pin the profile to ~/.xen/runtime/chrome-claude-profile on internal or M4.

Verified specifics, each one a reproduced result:

  • Real Chrome, not Chromium, not Chrome for Testing. The dedicated --user-data-dir is mandatory, not stylistic: launching against the default profile dir printed DevTools remote debugging requires a non-default data directory and the port never opened [VERIFIED — local, reproduced verbatim on Chrome 150; policy at https://developer.chrome.com/blog/remote-debugging-port].
  • Do NOT use --auto-accept-camera-and-microphone-capture. Measured side by side: the flag route gets getUserMedia through in 771 ms against the real device but leaves permissions.query({name:'microphone'}).state === "prompt" and enumerateDevices() labels hidden. The persisted-content-setting route yields "granted" with full real device labels [VERIFIED — local]. Claude's UI may gate on permissions.query(); the flag route would fail that gate [INFERRED].
  • Grant the mic once through the UI in that profile, then let Chrome write profile.content_settings.exceptions.media_stream_mic → {"https://claude.ai,*": {"setting": 1}} into $PROFILE/Default/Preferences itself. Hand-seeding that JSON works and survived a kill/relaunch cycle [VERIFIED — local] but was only tested on one Chrome version — UI-grant is the durable production form [INFERRED].
  • Cold-restart durability proven: full process kill → relaunch with no media flag and no reseeding → permQuery='granted', gUM OK in 656 ms, real device labels visible, AudioContext.state === 'running', and a written cookie + localStorage value read back byte-identical [VERIFIED — local]. macOS TCC is per-bundle-id not per-profile, so the dedicated profile costs nothing at OS level — kTCCServiceMicrophone|com.google.Chrome|2 already present [VERIFIED — local].
  • --disable-session-crashed-bubble is removed from the shipping binary; --hide-crash-restore-bubble is present [VERIFIED — local, strings on Google Chrome Framework 150.0.7871.181].

  • Attach mode works and was executed live against an externally-launched Chrome 150: Stagehand 3.7.1 attached and read a tab that predated it, extract() returned that tab's real accessibility tree over the attached connection [VERIFIED — local].
  • cdpUrl is real in v3 (v3.js:726: "If a CDP URL is provided, attach instead of launching") but is absent from the v3 docs page [VERIFIED — https://docs.stagehand.dev/v3/configuration/browser]. Pin @browserbasehq/stagehand@3.7.1.
  • The documented cdpUrl: 'http://localhost:9222' form FAILS in 3.7.1 — Unexpected server response: 404, reproduced 3×. Only the full ws://host:port/devtools/browser/<uuid> target works; Stagehand only resolves /json/version on its own launch path [VERIFIED — local].
  • sh.close() does not kill an externally-attached browser (source ships a stub kill: async () => {}; measured: process still alive after close) [VERIFIED — local]. This is exactly what supervision wants — controller and browser become independently restartable units.
  • Do not pass an externally-created Playwright page into Stagehand: Failed to resolve V3 Page from Playwright page [VERIFIED — https://github.com/browserbase/stagehand/issues/1392].
  • act/observe are un-gated by env (grep of v3.js:989–1200 for env ===|BROWSERBASE|LOCAL → zero hits) [VERIFIED — local], but a full LLM-backed round trip was never run — no valid model key was present. The inference step is INFERRED, not observed.

THE ONE TEST — 40 minutes, kills or proves the whole approach

Run it as a single sitting, in this order, and stop at the first failure. It collapses four unknowns into one experiment.

  1. (5 min) Physical mic routed, default input set to it, measured RMS > 1e-4.
  2. (5 min) Launch the line above. Grant the mic prompt once, by hand, in that profile. Confirm /json/version returns the UUID you expect — twice in this swarm the wrong browser answered because 9222/9333/9200 are occupied by Comet, a headless Chrome, and browseros [VERIFIED — local].
  3. (5 min) GATE 1 — Cloudflare. Does claude.ai render app DOM, or an interstitial? Assert document.querySelectorAll('[data-testid]').length > 0. This failed in the swarm on a fresh automation profile. If it fails here too, try the same launch against a copy of qi's normal daily profile rather than a virgin one. If it still fails, the entire PRD is blocked on bot management and nothing downstream matters.
  4. (10 min) GATE 2 — the closed voice loop. Log in. Click the voice button. Say one sentence out loud. Hear the reply out of the speakers. Screenshot the voice UI (C17). This is the gate the PRD never had — the review was right about that, and it is the single most valuable thing in the review.
  5. (10 min) GATE 3 — transcript timing, the one that decides the bridge shape. With the voice session still open, poll https://claude.ai/api/organizations/{orgId}/chat_conversations/{convId}?tree=True&rendering_mode=messages&render_all_tools=true (the endpoint used independently by four shipped exporters [VERIFIED — https://github.com/socketteer/Claude-Conversation-Exporter, https://github.com/agarwalvishal/claude-chat-exporter, https://github.com/lekandigital/claude-export-hub, https://github.com/Llaves/ClaudeExport]). Does the utterance appear per turn, or only after ending the voice session? Then end the session and poll again.
  6. (5 min) GATE 4 — attach. Point the Stagehand snippet at that same running Chrome; assert it sees the claude.ai tab and extract() returns real content, without disturbing the voice session.

Failure semantics: Gate 1 fail → bot-management spike, PRD blocked. Gate 2 fail → Voice Mode is not automatable-adjacent at all; plane-split becomes the only design. Gate 3 "session-end only" → the JSON endpoint has session-length latency and FR5 must move to a MutationObserver on the voice overlay or to local audio transcription. Gate 4 fail → tmux owns the browser and Stagehand launches it instead of attaching.

Run this in parallel with it (20 min, independent): the plane-split probe. Open Voice Mode on the phone in conversation X; from tmux, inject a text message into conversation X via the same JSON API surface; speak a turn and see whether Claude's live voice turn has the injected text in context. If yes, the plane-split is available, ToS exposure drops sharply, and the mic transport problem evaporates.

4. ANSWERS TO THE PRD'S FOUR OPEN QUESTIONS

Q1 — "Does the exact Claude web Voice Mode control surface remain fully usable in the persistent browser session path?" Unanswerable from research; reclassify from Open Question to Phase 0 gate. Anthropic publishes no browser/headless statement about Voice Mode [VERIFIED — https://support.claude.com/en/articles/11101966-use-voice-mode]; Browserbase publishes nothing about audio devices [VERIFIED — https://docs.browserbase.com/llms.txt]. Neither side documents it, so no amount of reading resolves it. What the swarm can answer: on Browserbase specifically it is unusable — no audio parameter and no launch-args field exist to make a media device appear [VERIFIED — https://docs.browserbase.com/reference/api/create-a-session]. On a local persistent profile the prerequisites all hold — permissions.query() === "granted", real device labels, AudioContext running, all durable across cold restart [VERIFIED — local]. Whether Claude's own voice client needs anything beyond getUserMedia + AudioContext is unknown and is Gate 2.

Q2 — "What transcript granularity: raw utterances, summarized checkpoints, or both?" Both, with a named mechanism the PRD lacks. Raw and durable = the private conversation JSON message tree, keyed and deduped by message uuid — not scraped innerText [VERIFIED — four independent exporter codebases, URLs above]. Summaries derived downstream in tmux. Trigger = a MutationObserver on [data-is-streaming] (a live-state attribute, the only DOM marker with real-world usage evidence) firing the fetch — not a polling drainer, which satisfies C30 [VERIFIED — same codebases]. DOM text scraping is fallback only. Voice mode is turn-based rather than duplex [VERIFIED — https://dataconomy.com/2026/07/24/anthropic-upgrades-claude-voice-mode-with-sonnet/], so the natural unit is a completed utterance and sub-second word streaming buys nothing. Caveat that could invert this: if Gate 3 shows transcripts persist only at session end, the JSON endpoint has session-length latency and the observer must read the live voice overlay instead — and those selectors are entirely unverified, because Cloudflare blocked the app DOM from ever loading in the automated browser [VERIFIED — local].

Q3 — "What recovery policy when Voice Mode exits unexpectedly: immediate re-entry, staged retry, or operator alert?" Immediate re-entry, but only after a precheck sequence the PRD's recovery order omits entirely. The PRD's order is reconnect → re-observe → reacquire → resume. Insert three steps at the front, each derived from a failure actually reproduced in this swarm:

  1. Assert the CDP browser UUID matches the supervised process. Twice the swarm talked to a different browser on the expected port (Comet on 9222, a headless Chrome on 9333, browseros on 9200) [VERIFIED — local]. Reconnecting to the wrong browser looks like success and is total failure.
  2. Assert input device presence, correct binding, and non-zero signal. Nine selectable inputs on this Mac, all virtual, default currently in [VERIFIED — local]. "Bound to the wrong device" and "bound to a silent device" are the two failure modes that pass every other health check.
  3. Assert permissions.query({name:'microphone'}).state === "granted" and enumerateDevices() returns non-empty labels — both cheap, both machine-checkable, both currently absent from any profile on this box [VERIFIED — local].

Then immediate re-entry, escalating to operator alert only after N failures. Operator alert as the first response violates C4. The local-audio tap (BlackHole 2ch, ffmpeg, sox all already installed; only a whisper.cpp streaming build missing [VERIFIED — local]) is the right sensor for "session looks green, no sound reached the room" — that is its correct role, not as a transcript source, because a transcript derived from room audio silently diverges from what Anthropic's ASR actually put in Claude's context, and silent divergence is worse than a stale read [INFERRED].

Q4 — "Which model should power Stagehand first, before OmniRoute?" The swarm did not establish this and I will not guess. No LLM-backed observe/act round trip was ever completed — no valid model key existed in the test environment; act/observe reached the inference layer and failed with API key not valid, which proves the browser layer hands off correctly and proves nothing about model fitness [VERIFIED — local]. What the swarm does constrain: pin @browserbasehq/stagehand@3.7.1, because cdpUrl is an undocumented surface on v3 [VERIFIED — https://docs.stagehand.dev/v3/configuration/browser] and could shift without notice; and defer OmniRoute exactly as the PRD says, since a routing layer would make model failures indistinguishable from browser failures during the phase where both are unproven [INFERRED]. Pick the model empirically after Gate 4, on one metric: can it find and click the voice button after a UI shift.

5. WHAT REMAINS UNKNOWN

Listed because it is unknown, not to look thorough. Nothing here is padding and nothing verified has been demoted to hide a weakness.

Blocking unknowns — these decide the project:

  1. Whether Claude web Voice Mode functions end-to-end in a script-launched local Chrome. Never tested. Gate 2. This is the unknown.
  2. Whether an automation-flagged Chrome can reach claude.ai at all. Reproduced failure on a fresh profile [VERIFIED — local]; whether a copy of qi's daily profile survives the challenge is untested. Gate 1.
  3. When a voice turn persists to the conversation record — per utterance or at session end. Anthropic's docs say transcripts are saved but never state timing (independently re-confirmed 2026-07-31) [VERIFIED — https://support.claude.com/en/articles/11101966-use-voice-mode]. The entire FR5 shape hinges on it. Gate 3.
  4. Whether a physical microphone even exists on this Mac and is merely unrouted, versus the routing graph needing a rebuild. All nine inputs virtual, measured RMS 0.000 [VERIFIED — local]; the cause is not established.
  5. Whether Anthropic treats a user automating their own single consumer account differently from a third party reselling access. §3(7) contains no personal-use carve-out [VERIFIED — https://www.anthropic.com/legal/consumer-terms], and I found no published enforcement statement or clarification addressing self-automation specifically. The documented enforcement wave targeted OAuth extraction and third-party harnesses — adjacent, not identical. This is a genuine unknown with account-termination downside, and it is qi's call, not an engineering question.

Substantive unknowns:

  1. Which media transport Voice Mode uses in the browser (getUserMedia + WebSocket vs WebRTC). Undetermined — and decisive for FR5's fallback, because if it is WebRTC then neither Playwright's framereceived nor CDP's webSocketFrameReceived will see anything and there is no frame-level tap for WebRTC media. Search results conflated Anthropic's implementation with an unrelated third-party LiveKit "voice-mode" project; those claims are not asserted here.
  2. Every voice-overlay selector — the container, any live/partial transcript element, the mic and end-call controls. All unverified: Cloudflare prevented the app DOM from loading, and none of the four exporter codebases touch voice UI. Every selector named in this document comes from text-chat surfaces only.
  3. Whether the plane-split's write direction works — tmux-injected text picked up by a live voice turn. Untested, and the cleanest version of it (Claude calling tmux tools mid-turn) has adjacent evidence against it.
  4. Round-trip latency for neko/Kasm mic passthrough under real conditions. Nobody publishes it. Barge-in viability depends on it. Also: no published report of Claude Voice Mode running inside either.
  5. Whether Voice Mode's VAD/turn detection behaves acceptably with a virtual input device (Loopback, BlackHole, Jump Desktop Microphone) rather than a real mic — and specifically with 8 kHz narrowband PSTN audio. Zero audio tests were run. This would fail silently.
  6. Whether Jump Desktop's iOS client has shipped mic forwarding since the changelog entry ("not supported on iPad… actively working on it", undated). This matters more than its size suggests — the iPhone is qi's only currently-online remote device.
  7. Stability, rate limits, and ToS posture of the private /api/organizations/.../chat_conversations endpoint. Undocumented, unversioned. Every consumer found is a manual export tool; nobody has published evidence about sustained polling.
  8. Whether Chrome can capture a forwarded mic while the Mac's display is asleep or locked. Untested, and the likeliest silent failure for any unattended-Mac assumption.
  9. Hyperbrowser: could not verify at all. Both documented URLs failed (308-redirect then 404). No evidence of audio support and no evidence of its absence — treat as unverified, not as a no.
