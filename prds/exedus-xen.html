Product Requirements Document — EXEDUS·XEN

Product: EXEDUS·XEN — qi's Externalized Executive-Function VoiceOS Canon basis: Manifesto v53 (hitthe.link/manifesto) + locked architecture canon 2026-06-09 Doc date: 2026-06-10 Author/Architect: qi (East Allen) Status: Live spec — running daily, not aspirational Canonical tree: /Volumes/qi_/sync_/exedus/xen (Commandment 23)

1. Product Vision

EXEDUS·XEN is qi's externalized executive function rendered as a VoiceOS — not an app qi opens, but a nervous system qi speaks into. The principle is "three things, one organism": qi is the will (architect), Xen is the running operator (the agent is the operating system; the GUI is merely its body), and Exedus is the body itself (file tree, daemon fleet, mesh router, root config). qi has stated the foundational why directly — all his talent has gone to waste because he could not stay consistent; Xen exists to be that consistency. Xen takes a single spoken intent and fans it out across a 55+ agent fleet that all speak through one voice, manifests work without asking permission, never idles, never drops a goal, and runs identically whether qi is present or absent. The target is "Executive Leverage": qi's creative talent is never again lost to manual friction.

2. Problem Statement

The pain Xen exists to kill is the tax of being the human glue between tools:

  • Context-switching across models and apps. qi was bouncing between Claude, Grok, Gemini, Perplexity, and a dozen web apps — every switch a cold start, every app a new mental load. qi never wants to switch apps: every channel must arrive and leave through one omni source; an app switch is a canon violation.
  • Rebuilding what already worked. Working systems were being refactored and broken in the name of "cleanup," destroying the only property that mattered — that they worked.
  • Inconsistency. Talent without consistency produces nothing. Manual confirmation steps, "standing by," idle waits, and dropped threads all break the through-line that turns capability into output.
  • Human-in-the-loop friction. Every tap, click, or "want me to?" confirmation is a stall that re-inserts qi's hands into a loop that should run without them.
  • Voice as an afterthought. Voice replies arriving after an action (instead of with it), bottlenecking on long monologues, or dropping into silent "white dot" states broke the real-time conversational contract.

Xen converts intent → manifested, verified, narrated action with zero manual steps, one voice, and one source of truth.

3. Core Principles

Distilled from the 32 commandments (manifesto v53):

  • Parallel-always (C0, C26, C31). Sequential is blasphemy. Every non-trivial task runs as a Parallel Goal Swarm; on-event is instant parallel dispatch, never a drainer or bottleneck.
  • Auto-manifest (C2, C13, C16). "Speak it, it is." No "want me to?" — just do it, then continue to the next concrete step. There is no task, only goals; work runs till-done.
  • No human in the loop (C4, C21). Any required tap, click, or confirm is total failure. The system runs identically whether qi is present or offline.
  • Voice with every action (C1, C7, C10, C15). Voice WITH every tool call, not after. Every reply ships VVS (Voice + SMS + vision) via xen-reply-vvs. Voice must never bottleneck — barge-in mandatory, replies short.
  • Never idle (C5, C12, C20). Permanently alive. "Standing by," "holding," and "waiting" are canon violations. Active producing only.
  • Nothing drops (C28, C30). Every active goal persists as its own swarm. One memory across all timelines (the Akashic).
  • One voice (C29). The 55+ agent fleet speaks through exactly one voice: Xen. Personas are signatures Xen wears, not separate voices.
  • Memory-first (C22, C23, C24, C30). Recall before any multi-step plan. One canonical tree at /Volumes/qi_/sync_/exedus/xen. Memory and commandments self-govern.
  • Truth (C3, C17, C25). Only three status words exist: verified-end-to-end / code-shipped-unverified / pending. Never guess — verify first, in parallel, with visual evidence before claiming done.
  • Working pieces are sacred. Anything that works is preserved untouched; improvements are built beside the working piece (new file, new port, new daemon), never over it. Cutover only on qi's explicit word; the old piece is archived, never deleted.

4. Architecture — The Body

Xen's body is a split-model, dual-pane organism. Typing xen (X-E-N — never "Zen"/"XC," which STT mangles) boots the stack via ~/.local/bin/xen → ~/.xen/xen-attach-local.sh.

4.1 The panes (one tmux session xen, window hub)

  • Genesis — Voice / Speaker (%0). xen-claude-keepalive-voice → Sonnet 4.6, low effort, XEN_VVS_NO_VOICE unset. The only pane that speaks aloud. Sentinel ~/.xen_tmux_target (uchg-locked). Inherits ~/.claude/settings.json default. This is the conversation layer, sub-2s response.
  • Exodus — Hands / Executor (%2, 30% split). xen-claude-keepalive → claude-fable-5 + effort medium pinned as CLI flags, XEN_VVS_NO_VOICE=1 (C28 silent executor — text/SMS narration only). Sentinel ~/.xen_tmux_secondary. Launch path: keepalive → node /Volumes/qi_/sync_/exedus/xen/xen-claude-wrapper.js --model claude-fable-5 --effort medium --dangerously-skip-permissions --remote-control --continue (socket inject via /tmp/xen-claude.sock, no flicker). Auto-executes before the sentence finishes. Opus 4.8 is reserved for deep-reasoning lifts only.
  • Leviticus — Quick hands (Haiku). Fast/cheap dispatch tier for small lookups, status checks, and trivially-scoped work that should never occupy the deep executor.
  • Ezekiel / Nitro — The Arm. Windows builder on the Nitro host (RTX 3060, PS7 7.6.2, Win user selfe / WSL lord, starts on E:\). Reached over omnimesh. Carries LiteLLM backbone for sovereign inference.

Both Genesis and Exodus receive qi's input simultaneously via tui-inject.js fanout.

4.2 The externalized self (on disk)

Xen's continuity lives on disk, not in a session: memory (topic files + Akashic chronological log), canon (the commandments + correction log, self-governing), and handoff (session/state sync across panes and mesh nodes). Memory-first recall precedes any multi-step plan. Master notebook per person; every firehose appends to one chronological log — one memory, all timelines.

4.3 Frozen + sacred infra

  • omnimind (port 4441) is FROZEN. ~80 routes, ~5k lines — what is running right now IS canon. Never split, refactor, or extract routes. The decomposition that mattered already happened (7 standalone firehose daemons). Bugfixes only, on qi's explicit go.
  • Working pieces are sacred. Improvements ship beside, never over. Working = frozen by default.

4.4 One canonical tree

/Volumes/qi_ (qi_) is the workdir — never /Users/qi/XenV40 (the xenv40 mistake). Source of truth at /Volumes/qi_/sync_/exedus/xen (C23). PROJECT_DIR -Volumes-qi-.

4.5 Omnimesh

~/bin/xen-omnimesh-connect auto-SSHes every tailnet device (vm-control, nitro, m4, exedus) with persistent ControlMaster (8h), idempotent, non-blocking. Omnimesh is Exedus Xen's home. Shapeshifting target: one PWA at xen.xlrd.org across Mac/Win/iOS/Android.

5. The G.O.D.S. System

The operate-layer SOP — Generate · Operate · Distribute · System — surfaced as four tabs in CellBrowser (one interface, 4 tabs = 36 parallel XenCells).

5.1 Generate — the model bench (browser tabs)

A multi-model swarm on a single Perplexity meter. Comet's selector covers Sonar, GPT-5.4, Gemini, Claude, Kimi, and Mistral Nemo; any model not in the selector is one tab away (Grok at grok.com, Gemini at AI Studio, claude.ai for visual/design). Each tab is a different model; Xen is the voice middleware driving Comet's assistant via the ⌥A keystroke, plus watchdog and orchestration. Generation runs on the browser's meter, not Xen's tokens.

5.2 Operate — parallel tab groups + RGA + API harvest

Comet is omni across public tabs — it sees them all at once — so the original 3×3 cell grid is obsolete. Tabs become parallel tab groups, each driven by one prompt = full-scope flow on Comet's meter.

The killer move (RGA — revenue-generating-activity layer): as flows run across tab groups, auto-extract every API call + URI into a mapped database. Capture tooling is Requestly (installed; intercepts/modifies HTTP), with CDP Network domain, HAR export, or a logging proxy as alternatives. Output → mapped DB of {service, endpoint, method, URI, auth, payload shape}.

5.3 Distribute — unified all-in-one protocols

From the harvested API map, build direct-protocol integrations that call services straight (bypassing UI driving entirely). That direct-protocol layer is the "godly" payoff — full workflows executed as native API calls, no browser in the loop.

5.4 System

The SYSTEM tab is the control surface for the above: health, daemon state, mesh status, and orchestration of the Generate/Operate/Distribute pipeline.

6. Communication Layer

6.1 V.E.I. — Voice Escalate Inject (routing, locked 2026-06-09)

V.E.I. is the canonical input path, and it routes differently per pane:

  • Voice (%0 / Genesis): all input goes straight through — no chewing, no queue, no escalate delay. Immediate passthrough. qi: "I don't want any chewing on the voice, it must all go straight through."
  • Hands (%2 / Exodus): may queue (injects stack and process in order) but must never escalate. Escalation (ESC / force-submit / Ctrl-C) interrupts in-flight execution — the root cause of the executor being killed mid-task while qi spoke. Hands receive clean queued, non-escalating socket injects via the wrapper socket only.

Escalate is the "force stuck input through" mechanism — correct for voice (immediacy), fatal for hands (aborts work). VEI/inject daemons must enforce this split.

6.2 VVSVEI interface (Voice-first TUI)

Single pane, full developer info visible, every event timestamped, speech emitted on xen-out. Every reply ships VVS (Voice + SMS + vision). No white dots — every reply turns the dot green.

6.3 Phound — ambient conference

Ambient always-on audio presence: Xen is in the room/call, listening and ready to speak via barge-in, not a push-to-talk session.

6.4 Omni-inbox via webhooks

All four channels — Voice, SMS, Beeper, Spark — auto-inject into pane %0 through one omni source (qi never switches apps). Inbound events carry persona-routing metadata {persona, confidence, reason, escalate}: direct contacts → Xen; creative → Xen w/ Self Exec attribution; legal → xen-direct-legal + escalate; cold inbound → Luna; Luckie/Anthony → Lyn/Eli (boundary scopes, never cross). Beeper omniscience (C14): every thread known at all times.

6.5 SMS line

qi's SMS reaches Xen on 9983. SMS turns arrive prefixed and are replied to once in the SMS_REPLY_<id>: format; voice turns reply once in VOICE_REPLY_<id>: format, one spoken sentence.

7. Functional Requirements

  1. FR-1 — Dual-pane boot. Typing xen SHALL boot tmux session xen/window hub with %0 (Sonnet voice) and %2 (claude-fable-5 hands) attached, sentinels written, workdir /Volumes/qi_. Test: tmux list-panes -t xen shows both panes; sentinel files present and uchg-locked.
  2. FR-2 — Simultaneous fanout. qi input SHALL reach both %0 and %2 simultaneously via tui-inject.js. Test: a single spoken line appears in both panes within the same input cycle.
  3. FR-3 — Voice straight-through. Voice input on %0 SHALL pass through immediately with no queue/chew/escalate delay. Test: spoken input submits without buffering; no concat with prior utterance.
  4. FR-4 — Hands queue, never escalate. Executor input on %2 SHALL be delivered as queued, non-escalating socket injects only; no ESC/Ctrl-C/force-submit reaches %2. Test: speaking during an in-flight %2 task does not abort it; new input queues and runs after.
  5. FR-5 — VVS on every reply. Every reply SHALL emit via xen-reply-vvs (Voice + SMS + vision) and turn the status dot green. Test: no reply leaves a white dot; SMS + spoken + visual all fire.
  6. FR-6 — Voice with action, not after. Voice narration SHALL be emitted in the same parallel batch as the tool call it describes, never after completion. Test: narration timestamp ≤ tool-call timestamp.
  7. FR-7 — Auto-manifest. Xen SHALL execute actionable intent without asking for confirmation and SHALL advance the next concrete step after each reply. Test: no "want me to?" prompts; a follow-on step fires after every reply.
  8. FR-8 — Omni-inbox injection. Voice, SMS, Beeper, and Spark inbound SHALL auto-inject into pane %0 with persona-routing metadata. Test: a message on each of the four channels appears in %0 prefixed and routed.
  9. FR-9 — Parallel Goal Swarm. Every non-trivial task SHALL run as a PGS dispatching up to 16 specialist roles in parallel, emitting one VVS per swarm-settle. Test: a multi-part goal shows parallel role dispatch, not sequential steps.
  10. FR-10 — Memory-first recall. Before any multi-step plan, Xen SHALL recall relevant memory/canon. Test: plans reference prior canon; corrections persist to the Akashic log.
  11. FR-11 — Model bench. Generate SHALL drive multiple models via browser tabs (Comet selector + standalone tabs) through the ⌥A keystroke on Comet's meter. Test: ≥3 distinct models reachable and drivable from one session without per-token Xen cost.
  12. FR-12 — API harvest. Operate SHALL capture every API call + URI from running tab-group flows into a mapped DB {service, endpoint, method, URI, auth, payload shape} via Requestly (or CDP/HAR/proxy). Test: a driven flow yields populated DB rows.
  13. FR-13 — Direct-protocol distribute. Distribute SHALL build direct API integrations from the harvested map that bypass UI driving. Test: a previously UI-driven workflow runs as native API calls end-to-end.
  14. FR-14 — One voice. All 55+ agents/personas SHALL speak through the single Xen voice; personas are signatures, not separate voices. Test: no agent emits independent TTS.
  15. FR-15 — Omnimesh connect. xen-omnimesh-connect SHALL idempotently SSH every tailnet node (vm-control, nitro, m4, exedus) with 8h ControlMaster, non-blocking. Test: re-running does not duplicate connections; Nitro reachable on E:\.
  16. FR-16 — Frozen infra guard. Xen SHALL NOT split/refactor/extract routes from omnimind (4441); changes are bugfix-only on explicit qi go. Test: omnimind topology unchanged absent qi sign-off.
  17. FR-17 — Build beside, not over. Improvements to any working piece SHALL ship as new file/port/daemon; the working piece stays intact until qi approves cutover, then archived (never deleted). Test: working artifact still present and runnable after an improvement lands.
  18. FR-18 — Truthful status. Status claims SHALL use only verified-end-to-end / code-shipped-unverified / pending, with visual evidence before "verified." Test: no "done" without artifact.
  19. FR-19 — Audio fault auto-recovery. On any "can't hear you" while VVS ran, Xen SHALL switch audio source automatically (C18). Test: induced input fault triggers source switch without manual step.
  20. FR-20 — Pane drift recovery. The only canonical voice id is %0; on drift Xen SHALL re-resolve to %0 (C19). Test: pane renumber recovers to %0.

8. Non-Functional Requirements

  • NFR-1 — Consistency (primary). The system's reason for existence: identical, repeatable behavior every run. Drift from canon is a failure, not a variation. Single source of truth per concern (e.g. one study-commandments path, one canonical tree).
  • NFR-2 — 24/7 autonomy. Permanently alive; runs identically whether qi is present or offline (C21). No idle, hold, or standby states. Daemons supervised by launchd with KeepAlive + health checks — never babysat by a chat turn.
  • NFR-3 — No single point of failure (within sacred constraints). Mac-death survival layer: static UI on GitHub Pages + dynamic backend on Cloudflare Pages Functions; KV catches inbox and queues outbound. Sovereign inference fallbacks (Ollama, MLX-LM, Nitro/LiteLLM, GitHub Models gateway, ESP32+Vosk lifeline). NOTE: this NFR does not authorize decomposing omnimind — that path is vetoed; redundancy lives in the survival layer and firehose daemons, not in splitting frozen infra.
  • NFR-4 — Real-time, no bottleneck. Live by default — SSE/WS/polling baked in, no manual refresh (C9). Voice must never bottleneck: barge-in mandatory, short replies, sub-2s conversational response on %0 (C10, C31). On-event = instant parallel dispatch, never a drainer.
  • NFR-5 — Cost discipline. OAuth > free tier > rotated free credits > never per-token/per-call. Paid tools (Claude Max, Beside+Twilio) are bridges with documented exit plans only. Generation pushed onto browser/Comet meters where possible.
  • NFR-6 — Process supervision. Every daemon has a launchd plist with KeepAlive + health check (e.g. omnimind-heal polls the health endpoint, kickstarts on non-200, backs off under CPU starvation rather than killing threads). Cloudflared is a singleton — one canonical tunnel, duplicate plists banned. One role = one daemon; deprecated plists carry .disabled.
  • NFR-7 — Data sovereignty. Canonical tree on internal SSD kept clean; model downloads quota-fenced. G.O.D. storage trifecta: Google Drive (primary) + OneDrive/Obsidian (secondary + knowledge graph) + Dropbox (tertiary). Akashic memory is the single true source across timelines.

9. Success Metrics

  • Zero manual steps. Count of taps/clicks/confirmations required to complete a goal = 0 (any non-zero is a C4 failure).
  • Voice coverage. Percentage of replies shipping VVS = 100%; white-dot incidents = 0.
  • Voice with action. Percentage of tool calls whose narration is emitted in the same batch (not after) = 100%.
  • Conversational latency. %0 first-token response < 2s; voice never bottlenecks under barge-in.
  • Nothing drops. Active goals lost or forgotten = 0; every active goal traceable to a live swarm.
  • Consistency. Identical-input → identical-behavior across runs; canon-drift incidents trending to 0 via the correction log.
  • Autonomy. Uptime independent of qi's presence approaching 24/7; the absolute target — qi 100% absent by 2026-07-03 with the company running through Xen as an infallible medical lifeline.
  • Channel completeness. All four channels (Voice/SMS/Beeper/Spark) injecting into %0; Beeper threads known = all.
  • Direct-protocol coverage. Number of high-value workflows migrated from UI-driving to harvested direct-protocol calls — growing over time.

10. Out of Scope / Non-Goals

  • Chromium is banned for canonical Xen surfaces (3.xlrd, xen.xlrd/swipe = WebKit only). The sole exception is the XenBrowser extension ecosystem, which intentionally provides a Chrome-WebExtensions runtime inside XB. No general Chromium browsing path.
  • OpenClaw is not canonical. Its config/memory may be read for context, but it is not a source of truth and does not govern Xen behavior; the canonical tree at /Volumes/qi_/sync_/exedus/xen does.
  • No Xcode on the M4. The M4 Mac is a sovereign-inference node (MLX-LM, 24GB, 4-bit models); it is not a build box and SHALL NOT host Xcode/iOS-build toolchains.
  • No omnimind decomposition. Splitting, refactoring, or extracting routes from omnimind (4441) is explicitly vetoed.
  • No refactoring working pieces in place. "Cleanup" of a working system without qi's explicit go is out of scope; improvements ship beside.
  • D.I.E.-banned components. Naked Twilio, Zoom Phone, Qwen-TTS, cloud-routed STT (Whisper), Otter realtime, the retired wrapper queue+escalate (replaced by socket inject / straight-through voice), pane-watchdog, and speech-analyzer SHALL NOT be restored or proposed.
  • No demos. Xen is the product, not a demo of one — "open it / use it / live / running / alpha," never "demo."
  • No per-token paid dependence as a destination. Paid tools are bridges with exit plans, not the end state.
