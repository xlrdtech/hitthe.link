Two statements, one architecture: session 0 is the record and takes everything, always. Session 1 is the seat and takes only what you allow. A toggle governs the seat. Nothing governs the record.

01How an injection flows now

omni event→ rail muted?→ %0 · session 0 · always
…and only if NOT muted→ %1 · session 1 · seat

Before this change the mute dropped the pane inject for every pane, so muting a rail also erased it from the record. That is the defect the reload closes.

04The two things that changed

One config value and one gate branch. Nothing else was touched.

// 1 — ~/.xen_tmux_secondary   (the dual-pane fanout slot)
- %1   ← same as primary, so the fanout fanned to ONE pane and %0 got nothing
+ %0   ← the akashic door

// 2 — omnimind.js  ·  injectTui() gate
  if (rail && mutedRails().has(rail)) {
    logRailDrop(rail, label, body, opts && opts.log);
-   return { ok: true, injected: false, muted: true, rail };        // dropped for EVERY pane
+   const doorOnly = Object.assign({}, opts || {}, { doorOnly: true, seatMuted: true });
+   const r = __injectTuiUngated(label, body, doorOnly);            // still writes %0
+   return { ok: true, injected: false, muted: true, rail, door: !!(r && r.ok) };

doorOnly was not invented for this — tui-inject.js:399-408 already implemented it for ambient notification classes. The patch reuses the existing mechanism rather than adding a second way to route.

  • Your seat's primary target. ~/.xen_tmux_target is still %1. I did not move the door out from under you.
  • typed. Locked on at both ends, at every layer. Your typing reaches me no matter what any chip says.
  • The chip UI. Verified working end-to-end today — it POSTs /api/inject-sources, round-trips before painting, and shows ! when a mute does not land.
  • Retention. Every muted line is still written to inject-drops.jsonl as it always was. Now it also reaches the record itself.

Three things I would watch

  • Double-write on an unmuted rail. If both primary and secondary ever point at the same pane again, the fanout de-dups by pane ID — but if the sentinels drift apart onto two live panes, an unmuted rail lands twice. Session 0 has always de-duped by content in the day file; the seat does not.
  • Silence is now ambiguous. Before, a muted rail meant nothing was written anywhere. Now, quiet on the seat is normal and expected — so seat silence can no longer be used as evidence the rail is broken. Check the record, not the seat.
  • A second diverged copy exists. dev_/xen/tui-inject.js is a separate file from the live dev_/omnimind/tui-inject.js. Only the omnimind copy is loaded by :4441. If a future fix touches the wrong one it will look applied and do nothing.

# 2 — is a MUTED rail actually in the record?
tail -5 /Volumes/M4/akashic_/2026-08/$(date +%F)_part-002.md | grep -E 'omi:|bee:'

# 3 — what does the server think is muted?

If #1 is zero while you are speaking or #2 comes back empty, the rule is broken and this page is wrong. Those are the two checks that falsify it.
