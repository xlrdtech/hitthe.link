terminal-browser in use

v0.5.8 · zenbu-labs/terminal-browser

A real Chromium, painted into a terminal pane. Terminals that speak the kitty graphics protocol let a program hand pixels to the terminal, so the page renders where a shell would normally be — which means it opens in a split beside the conversation instead of stealing a window.

That geometry is the whole point. An agent and the page it is working on end up scoped to the same terminal tab, and terminal-browser action exposes that live tab as a CLI — snapshot, click, fill, eval. It replaced a browser-automation server that had timed out twice the same evening, and it works over SSH, so a site running on a remote machine previews locally with no tunnel.

code-server loopback only

VS Code over HTTP · coder/code-server

The editor runs on the machine that holds the tree; the browser is only the screen. Any device on the desk opens the same workspace, with the same extensions and the same terminal, and nothing has to be checked out twice.

It runs under launchd rather than a shell job on purpose. A backgrounded shell child gets reaped when its parent exits and leaves an empty log that reads exactly like a clean start — so "running" has to mean a supervisor that restarts it, not a process that happened to survive.

The 302 on / is the proof auth is on, and the 200 on /login is the proof the app is really there — a status code alone would have said neither.

Why it is not public. code-server is a full IDE with a terminal in it. Reachable from the internet without a gate, it is a remote shell on the machine holding everything — so the default here is the loopback interface and auth left on. Publishing it is a separate, deliberate decision, made through an authenticated tunnel, and it belongs to the person whose machine it is.
